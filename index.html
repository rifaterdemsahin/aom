✨ Adaptive Object Model · Joe Yoder + Ralph Johnson · then AI

The domain model is data. The code is an interpreter.

Joe Yoder’s Adaptive Object Model (AOM) stores classes, attributes, relationships, and rules as metadata that a running system interprets. That used to be expensive, rare, and hard to move. LLMs, rclone, and multiple specialized stores make the extra abstraction cheap.

📘 Open README.md 🐙 GitHub repo 🧠 adaptiveobjectmodel.com

Runtime, not compile time: the user-facing model is assembled from descriptions, not from a frozen class hierarchy.

🧭 Joe Yoder’s idea

In Architecture and Design of Adaptive Object-Models (Yoder, Johnson, and later WICSA work), an AOM is a reflective architecture: types live as instances. Users (often domain experts) change metadata — historically XML or a database — and the running system reflects those changes without a new compile of domain classes.

The slogan on Yoder’s site is the whole thesis: “Anything you can do, I can do meta…” If you want something to change quickly, you push it into data. The object model the user cares about is not the Java/C# class tree. The class tree is a small kernel that interprets the user’s model.

  • 📦 Metadata describes entities, properties, relationships, and rules.
  • 🔁 Interpreter / builder turns that metadata into live objects.
  • 🛠️ Editors let non-programmers change the model (the hard part, historically).
  • ⚡ Change the description → the running system changes. Controlled, but immediate.
“The object model that the user cares about is part of the database, and the object model of the code is just an interpreter of the users’ object model.” — Joseph W. Yoder & Ralph Johnson, The Adaptive Object-Model Architectural Style (2002)

🟦 Type Square — the structural core

AOM is not one pattern. It is a small language of patterns. The square at the center applies Type Object twice and Property once:

Four corners, one kernel: types describe instances; property types describe properties.

Around the square sit Accountability / Entity–Relationship (links between entities), Strategy and Rule Objects (behavior as data), then Builder, Interpreter, and an editor UI. Insurance products, medical observations, and workflow engines were the classic examples: many similar types, frequent change, non-programmers owning the “what.”

🧱 Type ObjectNew kinds of thing are instances of EntityType, not new subclasses.
🏷️ PropertyAttributes live in a bag, not as fixed fields on a class.
🔗 AccountabilityRelationships are first-class, typed, and configurable.
📜 Rule ObjectBusiness rules are objects the interpreter can run or compose.
🏗️ BuilderA build description constructs a valid AOM entity graph.
🗣️ InterpreterThe small coded kernel executes the large described model.

🪨 The old friction of extra-abstract models

AOM was always the right idea for domains that change faster than release trains. It was also a tax. You paid in architecture, tooling, and operations — before the business even got a new field.

😓 Then

  • You hand-built the Type Square, rule engine, and editors.
  • Metadata lived in one database or a pile of XML.
  • Moving the model meant ETL, dump files, and tribal knowledge.
  • Debugging meant staring at tables that are the program.
  • One wrong abstraction and you had a second, worse programming language.
  • Compile-time safety was gone; you had to invent your own.

😌 Now

  • An LLM can draft the meta-model, fixtures, and the interpreter glue.
  • Metadata is files: JSON, YAML, Markdown, SQLite, graph export.
  • rclone copies those files across Drive, S3, Azure Files, local disks.
  • You keep several stores: files, graph, vectors, tables — each for one job.
  • Natural language is a usable editor; code review still guards the kernel.
  • The extra layer is still abstract — it is no longer expensive to operate.

🤖 What changes with AI and LLM creation

Yoder’s kernel still matters: a small, boring interpreter is safer than generated class explosions. What collapsed is the cost of producing and revising the metadata.

  • 🧬 Generate the model. “Add a Claim type with amount, incident date, and a fraud-score rule” becomes EntityType + PropertyTypes + Rule Objects.
  • 🧪 Generate the tests. Golden entities, invalid property combinations, round-trip JSON.
  • 🪟 Generate the editor. Forms, Graph views, and prompts that write metadata instead of Java.
  • 🔌 Generate adapters. The same conceptual Entity can project to Postgres, Neo4j, Qdrant, and a folder of Markdown.
  • 🧹 Keep a tiny kernel. LLMs write the periphery; humans own Type Square invariants and rule safety.

The historic failure mode of AOM — inventing an accidental programming language nobody can debug — is still real. LLMs do not remove the need for a crisp meta-model. They remove the weeks of boilerplate between “we need a new type” and “the runtime has it.”

The LLM writes descriptions. The interpreter still runs them. That split is the whole architecture.

🚚 rclone: the model can move

Abstract models used to be stuck where they were born. AOM metadata in Oracle stayed in Oracle. rclone is “rsync for cloud storage”: one fs.Fs interface over local disks, S3, Azure Files, Google Drive, and seventy-plus backends, plus virtual layers (crypt, combine, alias, union).

That is the missing operational piece of 2002-era AOM. If EntityTypes are files, you can version them in git, sync them to a Shared Drive, mount them on a laptop, and restore them from object storage — without a custom metadata bus. Friction was never only in the UML. It was in getting the abstract model from here to there.

🗂️ Multiple data models, one conceptual AOM

Classic AOM often assumed one store. Today the same runtime model can project into several physical models. You do not pick a winner. You pick a job for each.

📄 Files (Markdown, YAML, JSON) Human edit, git, rclone, publishing Source of truth for EntityType / Rule text
🧮 Relational (Postgres, SQLite) Integrity, transactions, reports Property values, typed columns, constraints

🪄 The extra abstraction is finally cheap

Runtime models used to feel like too much architecture for too little shipping. The cost curve flipped:

1. CreationLLMs draft Type Squares, rules, and adapters in minutes. You review invariants instead of typing boilerplate.
2. Motionrclone and git treat metadata as ordinary files. The model is no longer trapped in one vendor database.
3. PluralityGraph, vectors, tables, and files can all be projections of one conceptual AOM. You stop fighting for a single physical schema.
4. EditingNatural language, Markdown, and generated UIs replace the custom “business rules workbench” that used to take a year.

What does not change: if the interpreter is sloppy, you have an untyped Lisp in your domain. Keep the kernel small. Keep rules explicit. Keep one conceptual Type Square even when you have four physical stores. AOM was never “don’t write code.” It was “don’t freeze the user’s world in classes.”
